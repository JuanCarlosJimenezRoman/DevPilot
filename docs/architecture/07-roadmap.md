# 07 — Roadmap e incrementos (Fase J)

> **Revisado con Juan (2026-09-09).** Esta versión reemplaza el roadmap inicial: el Incremento 1 queda aún más angosto de lo propuesto originalmente — ni siquiera incluye Project Knowledge/Session Memory/Decision Records todavía — para poder validar la hipótesis central lo antes posible y con datos medibles, no solo con intuición.

Principio: cada incremento debe terminar en algo que se pueda ejecutar y probar de punta a punta. La hipótesis central que hay que probar primero, y de la que depende todo lo demás, es angosta y concreta:

```
Proyecto
 ↓
Contexto persistente (mínimo)
 ↓
Context Pack
 ↓
IA web (DeepSeek / Claude / ChatGPT)
 ↓
Respuesta
 ↓
Import (parser de 3 capas)
 ↓
Diff
 ↓
Apply
```

Si esta cadena funciona, el resto del roadmap es incrementar sofisticación sobre una base ya validada. Si no funciona, ninguna otra pieza (Git, Claude Code, memoria persistente) importa todavía.

- ✅ **HECHO (2026-09-09) — Tool Engine mínimo (`PermissionGuard`) + `devpilot apply`.** `devpilot apply` es la primera vez que DevPilot escribe algo en el disco del usuario, así que es también la primera implementación real (no solo diseñada en 05) del Tool Engine: `PermissionGuard` (`packages/core/src/tools/permissionGuard.ts`) clasifica cada operación en riesgo `write` (`create`/`edit`/`patch`) o `delete`, y siempre exige confirmación explícita — no existe un "aprobar todo" implícito, tal como 05 lo prohíbe para v1. `PathGuard` está integrado dentro del mismo `evaluatePermission` (no como módulo separado: en la práctica es un solo chequeo de "¿la ruta resuelta cae dentro de la raíz del proyecto?") y se re-evalúa dos veces — al armar el plan y otra vez justo antes de escribir, en `applyChange`, defensa en profundidad real y no solo cosmética.   - **Bug real encontrado y corregido durante las pruebas de este mismo incremento, no relacionado con el Tool Engine ni con la reconstrucción — un bug de Node, no de lógica de negocio**: la primera versión de la confirmación interactiva del CLI creaba una interfaz de `readline` nueva por cada pregunta (`createInterface` + `rl.question` + `rl.close()` dentro de una función `confirm()` llamada una vez por cambio). Probado con respuestas simuladas por stdin (`printf 'y\ny\ny\n' | devpilot apply`), el comando aplicaba el primer cambio y luego se quedaba colgado esperando la segunda respuesta para siempre, aunque el pipe ya la traía. Causa: `rl.close()` descarta el buffer interno de líneas de esa interfaz — cualquier línea ya disponible en el pipe pero no consumida todavía por esa instancia se pierde al cerrarla. Reutilizar una sola interfaz para todo el comando (en vez de una por pregunta) pareció resolverlo, pero expuso un segundo problema, más sutil: con stdin *no interactivo* (pipe, redirección, o `yes |`), Node lee todo el input disponible de una sola vez y la interfaz de `readline` se cierra sola en cuanto el pipe llega a EOF — como nuestro código hace trabajo asíncrono real entre pregunta y pregunta (reconstruir contenido, escribir a disco), la interfaz ya está cerrada para cuando se necesita la segunda pregunta, y `rl.question()` lanza `readline was closed` aunque el pipe traía de sobra las respuestas. Confirmado con un repro mínimo aislado (sin nada de DevPilot de por medio) antes de tocar el código real, para descartar que fuera un bug de nuestra lógica. **Corregido con un `Confirmer` que distingue los dos casos**: con una terminal real (`process.stdin.isTTY`), sigue preguntando una por una con `readline`, como espera un humano tecleando; sin TTY, lee TODO el stdin de una sola vez por adelantado (ya está completo en el pipe) y consume una línea por confirmación desde una cola en memoria, sin más llamadas a `readline` — si el input se agota antes de lo esperado, se trata como "no" con un aviso explícito en vez de colgarse. Esto no es solo un problema de cómo probamos `apply`: cualquier uso real de DevPilot en un script, en CI, o con `yes | devpilot apply --yes-to write` habría tenido el mismo problema silencioso.

**Bug real encontrado y corregido (mío, no reportado por el usuario) — recurrencia de uno ya documentado**: al actualizar el comentario de `knowledge_docs` en `schema.ts` con términos entre backticks (`` `id` ``, `` `custom` ``...), rompí el template literal de JS (`PROJECT_DB_SCHEMA`) que envuelve todo el SQL más abajo en el mismo archivo — un backtick dentro del comentario cierra ese literal antes de tiempo. `tsc -b` lo confirmó con errores reales (`TS1005`, `TS1443`) en vez de fallar silenciosamente. Es la segunda vez en este proyecto que se cae en esta misma clase de error (la primera quedó documentada en una sesión anterior sobre este mismo archivo). Corregido reescribiendo el comentario en ASCII plano, sin backticks ni acentos, y agregando dentro del comentario mismo una advertencia explícita para quien lo edite después.

### ✅ HECHO (2026-09-10): Refresco incremental de Project State (Indexer)

Cuarta y última pieza del Incremento 2. Le da un consumidor real a la tabla `files` (03) — existía desde el Incremento 0 (`CREATE TABLE IF NOT EXISTS`) completamente vacía, mismo patrón que `decisions`/`sessions`/`knowledge_docs` en las tres piezas anteriores — y a la columna `project_state.last_indexed_commit`, que tampoco tenía nunca un consumidor real: `projectService.ts` la copiaba de sí misma en cada `project add` (`previousState?.lastIndexedCommit ?? null`), así que se quedaba en `null` para siempre, sesión tras sesión, desde el Incremento 0.

- Nuevo módulo `indexer.ts` (`@devpilot/core`) con `reindexProject(db, rootPath, vcs, previousLastIndexedCommit)`, invocado por `addProject` (`devpilot project add`) justo después del Scanner. Decide entre tres modos, en este orden: **`skipped`** (el proyecto es git, ya tenía un índice, y el commit actual es igual al indexado la última vez — no se toca ni un archivo); **`incremental`** (el commit cambió y `git diff --name-status --no-renames <anterior>..<actual>` funciona — solo se (re)procesan las rutas que ese diff marca, nunca el resto del árbol); **`full`** (primer reindexado, proyecto sin git, o el commit anterior ya no existe en el historial local — mismo comportamiento que tenía `project add` antes de esta pieza). `--no-renames` es una simplificación deliberada de v1: un archivo movido se ve como borrar+crear en vez de una operación de "renombrar fila" más barata — el índice resultante es idéntico, y mover archivos es mucho menos frecuente que editarlos.
- Cada archivo indexado guarda hash sha256 del contenido, lenguaje (mismo detector por extensión que ya usaba el Scanner), tamaño, fecha de modificación, y el commit en el que se vio por última vez — `files.path` es `UNIQUE` (no `PRIMARY KEY`), así que reindexar una ruta ya indexada conserva su `id` original vía `ON CONFLICT(path) DO UPDATE` en vez de generar uno nuevo cada vez, mismo patrón de upsert por identidad natural que `upsertKnowledgeDoc`.
- `devpilot project add` ahora reporta el resultado en una línea nueva ("Índice de archivos: ..."), distinta según el modo — visible para el usuario, no un detalle interno invisible: cuántos archivos se agregaron/actualizaron/eliminaron, o que el reindexado se saltó por completo.

**Decisión de diseño deliberada, documentada para no revertirla sin querer más adelante**: esta pieza NO cambia de dónde lee sus archivos el Context Planner (`relevancePlanner.ts` sigue usando `listProjectFiles` — un recorrido en vivo del árbol — en cada `devpilot context`). El índice persistido solo se actualiza en `devpilot project add`, y sus rutas se comparan por commits git, así que no vería ediciones todavía sin commitear — que es exactamente el caso común de uso real (trabajar en una tarea antes de commitear). Hacer que el Context Planner dependiera del índice persistido habría sido un regresión real de correctitud a cambio de una ganancia de performance que 04 nunca pidió ahí explícitamente. El Indexer sí cumple lo que 04 describe literalmente para sí mismo ("reindexado incremental... esto es lo que hace viable usar DevPilot en repos grandes sin re-escanear todo en cada comando [de `project add`]"), sin tocar la garantía de correctitud del Context Planner. Extracción de símbolos/AST (`symbols`/`file_edges`) sigue fuera de alcance, diferida a más adelante — el renderer de este Indexer solo llena `files`.

**Bug real encontrado y corregido, mío, durante la validación sintética**: la primera versión del reindexado incremental no aplicaba las mismas reglas de ignorados (`.gitignore`/`.devpilotignore`/ignorados por defecto como `.devpilot/`) que ya usa el recorrido completo (`listProjectFiles`) — así que una ruta ignorada que igual aparece en `git diff --name-status` (ej. `.devpilot/` comiteado por accidente en un repo sin `.gitignore` que lo excluya, algo que le pasó al propio fixture de prueba) terminaba entrando al índice en modo incremental, dando un resultado distinto al que un reindexado completo del mismo estado del repo habría dado. Encontrado reproduciendo exactamente ese escenario (dos `project add` con un commit de por medio que agrega `.devpilot/*` sin ignorarlo) antes de dar la pieza por buena. Corregido exportando un `createIgnoreMatcher(rootPath)` desde `fileWalker.ts` (misma lógica de `ignore` que ya usaba el recorrido completo, ahora reutilizable) y aplicándolo a cada ruta que llega desde `git diff` antes de indexarla o borrarla.

**Validado sintéticamente** (fixture git aislado): primer `project add` → reindexado completo (4-5 archivos según el fixture); segundo `project add` sin cambios → `skipped`, cero archivos tocados; commit con una modificación + un archivo nuevo + un archivo borrado, tercer `project add` → `incremental` con conteos exactos (1 nuevo/1 actualizado/1 eliminado), confirmado además por SQL directa que `last_seen_commit` solo cambia en las filas realmente tocadas y que los ids se conservan entre reindexados; proyecto sin git → siempre `full` (limitación de v1 documentada); `last_indexed_commit` apuntando a un commit ya inexistente en el historial (simulando un rebase/force-push) → *fallback* seguro a `full` en vez de fallar; y el escenario del bug de ignorados de arriba, confirmando después del fix que `.devpilot/*` nunca entra al índice pese a aparecer en el diff de git.

**Validado además contra Camino al Deporte real y contra el propio repo de DevPilot**: `project add` sobre ambos proyectos dio reindexado completo la primera vez (112 y 296 archivos respectivamente) y `skipped` en una segunda corrida inmediata sin cambios. Sobre Camino al Deporte, un cambio real y deliberadamente inocuo (una línea agregada a `README.md` + un archivo Markdown de prueba nuevo) comiteado y revertido mostró el ciclo completo: `incremental` con 1 nuevo/1 actualizado al aplicar el cambio, y de nuevo `incremental` con 1 actualizado/1 eliminado al revertirlo — confirmado por hash SQL que `README.md` volvió a su hash original exacto y que el archivo de prueba desapareció del índice. `git status --short` quedó limpio salvo `.devpilot/` al terminar.

**Nota de proceso, no de código — vale la pena dejarla escrita**: para revertir el commit de prueba sobre Camino al Deporte se usó `git reset --hard HEAD~1`, que descarta cualquier cambio sin commitear en el árbol de trabajo, no solo el commit de prueba — sobre un proyecto real donde el usuario puede estar editando en vivo al mismo tiempo (como pasó en esta misma validación: aparecieron cambios reales del usuario en varios componentes de `frontend/src/components/store/` justo después), esto es más riesgoso de lo necesario. No se perdió nada esta vez (se confirmó que el contenido de esos archivos seguía teniendo las ediciones del usuario después del reset), pero el reset pudo haber coincidido mal con un guardado del usuario. Para la próxima vez que una validación necesite revertir un commit de prueba sobre un proyecto real: usar `git revert <commit>` en vez de `git reset --hard` — deshace solo los archivos de ese commit específico sin tocar el resto del árbol de trabajo, sea lo que sea que el usuario tenga sin commitear en ese momento.
